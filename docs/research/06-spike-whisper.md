# 調査ノート 06：whisper.cpp（large-v3-turbo）によるローカル日本語音声認識の検証

- 調査日：2026-09-15
- 環境：macOS 26、Apple M4、32GB RAM
- 作成：Claude Code のサブエージェント（Sonnet 5）による実装・検証。
- 前提：個人用アプリで「今日やったこと」を日本語で30秒〜3分話し、文字起こしして記録するために、whisper.cpp（Homebrew 版）+ large-v3-turbo モデルを使うことがすでに決まっている。この調査の目的は、実機で本当に動くか、日本語の精度と速度、Core ML（Apple製の機械学習フレームワーク。Metal より高速な場合がある）が使えるかを確かめることである。
- 検証コード一式は `spikes/whisper/`（`run.sh` に全コマンド、`samples/` にテスト音声、`results/` に生の出力とログ、`cer.py` に文字誤り率計算スクリプト）に置いた。
- ファイル名について：`docs/research/05-spike-whisper.md` という指定だったが、番号05はすでに別の調査（`05-spike-recorder.md`、ブラウザ側WAV録音の検証）に使われていたため、本ノートは連番を守って `06-spike-whisper.md` とした。

## 結論（先に）

1. **Homebrew の whisper.cpp 1.9.4 は実機で問題なく動作した。** `brew install whisper.cpp` だけでインストールでき、`whisper-cli` と `whisper-server` が使えた。GPU 支援は **Metal（Apple M4 の GPU を使う仕組み）が有効**で、**Core ML には対応していない**（後述のログで確認）。
2. **日本語の書き起こし自体の精度は、単語レベルでは高い。** 固有名詞や漢字表記のわずかな誤り（「線形代数」→「線形台数」、「対称」→「対象」、「直交」→「直行」）はあるが、意味は十分わかるレベルだった。ただし、これは合成音声（`say` コマンド）による読み上げであり、実際の人の声より発音が安定しているため、**精度は実際の使用より良く出ている可能性が高い**（下記「限界」参照）。
3. **重大な問題を1つ発見した：`whisper-cli` はデフォルト設定で、約70秒の音声のうち1文（英語の専門用語 React, useEffect, SQLite, API を含む1文）を丸ごと出力から落とした。** 文字誤り率（CER）にして約49〜50%という高い値になったのはこの脱落が原因である。一方、`whisper-server` に同じ音声を渡すと、この文も含めてほぼ全文が出力され、CER は約4.9%だった。原因を `-bs -1 -bo 2`（`whisper-server` のデフォルトのデコード設定に合わせたもの）で `whisper-cli` を再実行して切り分けようとしたが、それでも文の脱落は再現し、**デコード方式（ビームサーチかgreedyか）だけが原因ではないという結果になった**。`whisper-cli` と `whisper-server` の間に何らかの処理差があることまでは確認したが、根本原因は特定できていない（「確かめられなかったこと」参照）。実運用では **`whisper-server` 経由での利用、または `whisper-cli` の挙動をこの1点についてさらに調査することを推奨する。**
4. **無音に対するハルシネーション（存在しない音声を「聞こえた」ことにして出力する現象）を確認した。** 10秒の完全な無音を渡すと、`-l ja` 指定時は「ご視聴ありがとうございました」、言語自動判定時は英語で「you」という、YouTube動画の締め言葉に典型的な文字列が出力された。`--no-speech-thold`（無音判定のしきい値）を 0.6→0.9 に上げても、この事例では抑制されなかった。
5. **前後に無音3秒ずつを足しても、無音自体が新たな幻覚を生むことはなかった**が、本文の書き起こし内容は無音なしの場合と微妙に変わった（脱落した文の一部が今度は部分的に出力されるなど、出力は非決定的にぶれる）。
6. `-l ja` を指定しない場合、言語自動判定が英語（en）に誤判定し、書き起こし内容も意味の通らない英語になった。**日本語音声を扱うなら `-l ja` を明示的に指定すべき**という結論。
7. 初期プロンプト（`--prompt`）を与えると、"React" などの英単語がラテン文字表記になりやすくなる効果を確認した（プロンプトなしでは「リーアクト」のようにカタカナ音写になった）。句読点の量そのものに大きな差は見られなかった。
8. 速度は実用上十分速い。約70秒の音声の文字起こしに約5〜6秒（実時間比で約12〜14倍速）。量子化版（q5_0、ファイルサイズ約574MB、通常版は約1.5GB）でも速度・精度ともに通常版とほぼ同等だった。

## 1. インストールとビルド構成の確認

```
brew install whisper.cpp
```

- インストールされた実行ファイル（`/opt/homebrew/Cellar/whisper.cpp/1.9.4/bin/` → `/opt/homebrew/bin/` にリンク）：`whisper-cli`、`whisper-server`、`whisper-bench`、`whisper-command`、`whisper-stream`、`whisper-talk-llama`、`whisper-quantize`、`whisper-vad-speech-segments`、`whisper-lsp`、`parakeet-cli`、`parakeet-quantize`（後者2つは別モデル用の付属ツール）。
- `whisper-cli --help` 実行時のログに以下の行があり、ビルド構成を確認できた。

```
system_info: n_threads = 4 / 10 | WHISPER : VITISAI = 0 | COREML = 0 | OPENVINO = 0 | MTL : EMBED_LIBRARY = 1 | ...
```

  - `COREML = 0` → **Core ML 非対応でビルドされている。**
  - `MTL`（Metal）関連のログが多数出力され、`ggml_metal_device_init: GPU name: MTL0 (Apple M4)` として GPU が認識されている → **Metal 対応でビルドされている。**
- Homebrew の formula（`brew cat whisper.cpp`）の cmake オプションを確認したところ、`-DWHISPER_SDL2=ON` はあるが `-DWHISPER_COREML=ON` に相当する指定はなかった。これが `COREML = 0` の直接の理由である。

### Core ML を使うには何が必要か（調査のみ、今回はビルドしていない）

whisper.cpp の公式リポジトリの説明に基づく概要：

1. Xcode Command Line Tools と Python 環境（`coremltools` パッケージ）を用意する。
2. リポジトリに含まれる `models/generate-coreml-model.sh` を使い、使用する ggml モデル（例：large-v3-turbo）に対応する Core ML 版エンコーダー（`.mlmodelc`）を生成する。
3. `cmake` のビルドオプションに `-DWHISPER_COREML=1` を付けて自前でソースからビルドし直す。
4. 生成した `.mlmodelc` を ggml モデルファイルと同じディレクトリに配置し、実行時に自動で読み込まれる（whisper.cpp 側の実装として、モデルと同名の `.mlmodelc` があれば使う仕組みになっている）。

Homebrew 版はこの手順を踏んでいないため Core ML 非対応である。Metal だけでも実測で実時間の12〜14倍速が出ており、この個人用途（30秒〜3分の音声を都度書き起こす）では **Core ML なしで速度上の問題はない**という判断が妥当と考える。

`spikes/whisper/samples/` に作成（`.gitignore` で `spikes/whisper/samples/*.wav` を除外済み、原稿の `.txt` とスクリプトはコミット対象）。

## 4. 文字起こし結果

以下、モデルは特記なき限り通常版 `ggml-large-v3-turbo.bin`。実行環境は上記の通り（M4、10コア中デフォルト4スレッド使用）。CERの計算は `spikes/whisper/cer.py`（レーベンシュタイン距離ベース、空白と主な句読点を除去して比較。句読点や改行の差はCERに影響しない設定）。

### 4-1. 言語指定の有無

| 条件 | 出力（抜粋） | 所要時間 | CER |
|---|---|---|---|
| 言語自動判定（`-l` 指定なし） | 検出言語 `en`。"Today, I'm going to read the show." を3回繰り返す、意味の通らない英語 | 5.99秒（実時間比 約11.7倍速） | 97.3%（ほぼ完全に不一致） |
| `-l ja` 指定 | 日本語で概ね内容が通る文章（下記参照） | 5.15秒 | 49.6% |

自動判定は完全に失敗した。**日本語音声には `-l ja` を明示することが必須**という結論。

### 4-2. 初期プロンプトの有無（いずれも `-l ja`）

プロンプト文：「以下は、今日の学習内容を日本語で話した記録です。句読点を付けて書き起こしてください。React、useEffect、SQLite、API。」

| 条件 | 出力（全文） | 所要時間 | CER |
|---|---|---|---|
| プロンプトなし | 今日は、線形台数の固有値と固有ベクトルの章を読んだ。特に対角化の条件と対称行列なら必ず直行行列で対角化できることが印象に残った。固有値が重複する場合でも、対称行列であれば固有空間の次元が重複度と一致するので、結局は直行行列で対角化できるという点が面白かった。クリーンアップ関数の実行タイミングを実装しながら確認した。次回は、この固有値の話を実際の**リーアクト**のステートの設定にどう応用できるか、もう少し考えてみたい。 | 5.15秒 | 49.6% |
| プロンプトあり | 同内容だが、末尾が「実際の**React**のステートの設定にどう応用できるか」となり、英単語がラテン文字表記になった | 5.07秒 | 48.8% |

**この2つの出力に共通する重大な問題**：正解原稿の中盤にある「あとReactのuseEffectのクリーンアップ関数の実行タイミングを実装しながら確認した。依存配列に指定した値が変わるたびに、前回のクリーンアップ関数が呼ばれてから新しいエフェクトが実行される、という順番を実際にログを出して確かめた。APIから取得したデータをSQLiteに保存する処理と組み合わせたときに、クリーンアップを忘れると二重にリクエストが飛ぶことがあったので、そこは注意が必要だと感じた。」という約150字分（原稿全体365字中の約4割）が、「クリーンアップ関数の実行タイミングを実装しながら確認した。」の一文だけを残してほぼ丸ごと脱落した。CERが約49〜50%という高い値になっている主因はこの脱落であり、残っている部分の文字レベルの誤りは実際には少ない。プロンプトの有無はこの脱落自体には影響しなかった。

### 4-3. 無音ファイル（b）でのハルシネーション

| 条件 | 出力 |
|---|---|
| `-l ja` | 「ご視聴ありがとうございました」 |
| 言語自動判定（検出は `en`） | 「 you」 |
| `-l ja` + `--no-speech-thold 0.9`（デフォルト0.6から引き上げ） | 「ご視聴ありがとうございました」（変化なし） |

**10秒の完全な無音に対しても、whisper.cppは「無音です」とは言わず、もっともらしい文章を生成する。** これは whisper 系モデルでよく知られるハルシネーションで、YouTube動画の書き起こしデータで学習された影響とされる典型的な出力（「ご視聴ありがとうございました」「Thank you for watching」相当）が出た。`--no-speech-thold` を上げても今回のケースでは抑制できなかった。**実運用では、生成テキストが「ご視聴ありがとうございました」等の定型句と完全一致する場合に破棄する、無音区間検出（VAD）を別途はさむ、などの後処理が必要**と考えられる。

### 4-4. 前後無音パディング（c）の影響

`-l ja` で実行した結果、無音区間自体が新たな幻覚を生むことはなかったが、本文の書き起こし内容は非パディング版と完全には一致しなかった。具体的には、4-2で丸ごと脱落した中盤の文のうち「あとReactのUCファクトのクリーンアップ関数の実行タイミングを実装しながら確認した。」（"useEffect"が"UCファクト"に誤変換）と「飛ぶことがあったので、そこは注意が必要だと感じた。」という断片が、今回は部分的に出力された。CERは40.0%（脱落幅が減った分、非パディング版の49.6%より改善）。**同じ音声でも前後の無音パディインの有無で中盤の文の脱落度合いが変わる**という、出力の非決定性・不安定さを確認した。

### 4-5. JSON出力（`-oj`）

`whisper-cli -m <model> -f samples/sample_a.wav -l ja -oj -of results/08_json` を実行し、`results/08_json.json` が生成されることを確認した。セグメントごとに開始・終了タイムスタンプ（`00:00:00,000`形式と、ミリ秒の数値の両方）とテキストが入っている。例：

```json
{
  "timestamps": { "from": "00:00:00,000", "to": "00:00:04,680" },
  "offsets": { "from": 0, "to": 4680 },
  "text": "今日は、線形代数の固有値と固有ベクトルの章を読んだ。"
}
```

（このJSON出力では「線形代数」が正しく漢字変換されており、テキストのみ出力時の「線形台数」との揺れが確認できた。同じモデル・同じ入力でも実行のたびに細部が変わりうる。）

### 4-6. 速度オプション

| 条件 | 所要時間 |
|---|---|
| `-t 1`（スレッド数1） | 6.93秒 |
| `-t 8`（スレッド数8） | 5.10秒 |
| `-t 4`（デフォルト） | 約5.0〜5.2秒 |
| `-nfa`（Flash Attention無効） | 6.05秒 |

スレッド数を1→8に増やす、Flash Attentionを有効にする、のいずれも速度改善効果があった（1回ずつの計測のため誤差はあるが、方向としては一貫している）。約70秒の音声が常に5〜7秒程度で処理でき、実用上は初期設定のままで十分速い。

### 4-7. 量子化版（q5_0）

| モデル | サイズ | 所要時間 | CER（プロンプトなし） |
|---|---|---|---|
| 通常版 | 約1.51GB | 5.15秒 | 49.6% |
| q5_0量子化版 | 約547MB | 5.06秒 | 50.1% |

速度・精度ともにほぼ同等だった。ディスク容量を抑えたい場合はq5_0版で問題なさそうという結論（ただしこの1サンプルのみの比較であり、確度は高くない）。

### 4-8. `whisper-cli` と `whisper-server` の出力差（重要な発見）

同じ音声・同じ言語指定（`ja`）で `whisper-server` の `/inference` エンドポイントに投げたところ、`whisper-cli` では脱落していた中盤の文がほぼ全て出力された。

```
今日は、線形台数の固有値と固有ベクトルの章を読んだ。
特に対角化の条件と、対称行列なら必ず直行行列で対角化できることが印象に残った。
固有値が重複する場合でも、対称行列であれば固有空間の次元が重複度と一致するので、結局は直行行列で対角化できるという点が面白かった。
あと、ReactのUC-Effectのクリーンアップ関数の実行タイミングを実装しながら確認した。
位存配列に指定した値が変わるたびに、前回のクリーンアップ関数が呼ばれてから新しいエフェクトが実行される、という順番を実際にログを出して確かめた。
APIから取得したデータをSQL-Iとに保存する処理と組み合わせた時に、クリーンアップを忘れると二重にリクエストが飛ぶことがあったので、そこは注意が必要だと感じた。
次回は、この固有値の話を実際のReactのステートの設定にどう応用できるか、もう少し考えてみたい。
```

CERは4.9%（18文字の編集距離／363文字）と、`whisper-cli`の約49〜50%から大幅に改善した。単語レベルの誤り（"useEffect"→"UC-Effect"、"SQLite"→"SQL-Iと"、"依存"→"位存"）は残るが、文の脱落はなかった。

`whisper-cli --help` と `whisper-server --help` のデフォルト値を比較すると、デコード方式のデフォルトが異なる（`whisper-cli` はビームサーチ `beam-size=5, best-of=5`、`whisper-server` は `beam-size=-1`（greedy）、`best-of=2`）。この違いが原因かを確かめるため、`whisper-cli` を `-bs -1 -bo 2`（`whisper-server`と同じデコード設定）で再実行したが、**それでも中盤の文は脱落したまま**だった（結果は4-2のプロンプトなしと同一）。したがって、**デコード方式の違いだけでは説明がつかない**。`whisper-server` は内部で音声ファイルの読み込み・リサンプリング処理が `whisper-cli` と異なる可能性があるが、今回の調査ではそこまで切り分けられていない。

実運用上の結論：**この個人用アプリでは `whisper-cli` を直接呼ぶのではなく `whisper-server` 経由で使うか、`whisper-cli` でこの脱落が再現する条件をさらに絞り込む必要がある。**

## 5. `whisper-server` の起動確認

```
whisper-server -m ~/.cache/whisper-cpp/ggml-large-v3-turbo.bin --port 8089
```

- 起動ログに `whisper server listening at http://127.0.0.1:8089` が出力され、起動確認できた。
- ルート（`GET /`）に対して HTTP 200 を確認。
- 書き起こしエンドポイントは `POST /inference`（multipart/form-data）。リクエスト例：

```
curl -s http://127.0.0.1:8089/inference \
  -F file=@samples/sample_a.wav \
  -F language=ja \
  -F response_format=json
```

- レスポンスはJSON、`{"text": "（全文の書き起こし、セグメントごとに改行区切り）"}` という形式（HTTP 200）。`response_format=json` を指定した場合はこの単純な形式で、セグメントのタイムスタンプ入りの詳細な形式が欲しい場合は別のフォーマット指定（未検証）が必要と思われる。
- 確認後、`kill` でサーバープロセスを停止し、停止したことを `ps` で確認済み。

## していないこと・確かめられなかったこと

## 追加調査：文の脱落の切り分け

- 調査日：2026-09-15（同日、上記本編の後に実施。上限25分の追加調査）
- 目的：「`whisper-cli` が1文を丸ごと落とし `whisper-server` では落ちなかった」現象について、(1) 本番でどちらを使うべきか、(2) 同じ脱落が `whisper-server` 側でも起こり得るか、を判断すること。

### 結論（先に）

**原因を特定した。** `whisper-cli` に付けていた `-nt`（`--no-timestamps`、タイムスタンプを表示しない）オプションが、単なる表示上の省略ではなく、whisper.cpp のデコード処理そのものに渡される `wparams.no_timestamps` というパラメータを `true` にしていた。これによりデコーダーがタイムスタンプ用の特殊トークンを使わずに文字を生成するようになり、その結果として今回のサンプルでは中盤の1文（React/useEffect/API/SQLiteを含む部分）が丸ごと出力から失われていた。`-nt` を外す（タイムスタンプ付きで出力する）と、`whisper-cli` でも該当の文を含めてほぼ全文が出力され、CERは8.8%まで改善した（テキストのみ出力時の49.6%から大幅改善）。`whisper-server` へのリクエストでは `no_timestamps` パラメータを一度も指定しておらず、既定値の `false` のままだったため、同じ問題が起きていなかった、という説明で一貫している。

**本番での判断**：
- `whisper-cli` を使うなら、**`-nt` を付けずに実行し、出力からタイムスタンプ行を後処理で取り除く**（または `-oj` でJSON出力してテキスト部分だけ結合する）べきである。`-nt` 単体の使用は今回のサンプルで文の脱落を引き起こしたため避ける。
- `whisper-server` は、クライアント側が `no_timestamps=true` をリクエストに含めない限り、同じ脱落は起きないはずである（サーバー側のコード上、`no_timestamps` パラメータの扱いは `whisper-cli` の `-nt` と全く同じ仕組みでwhisper.cppのデコーダーに渡ることをソースコードで確認したため、`whisper-server` 側で `no_timestamps=true` を指定すれば理論上同じ脱落が再現するはずだが、実際にそのリクエストは試していない）。
- したがって「本番でどちらを使うか」については、**`whisper-cli` を `-nt` なし（タイムスタンプ有効）で使うか、`whisper-server` を `no_timestamps` を指定せずに使うか、のどちらでも同程度に安全**という結論になった。重要なのは実行ファイルの選択ではなく、**`no_timestamps`（`-nt` または `no_timestamps=true`）を有効にしないこと**である。

### 事実1：再現性（3回ずつ実行）

- `whisper-cli`（既定のビームサーチ設定、`-l ja -nt`）を同じ `sample_a.wav` に対して3回実行した結果、**3回とも文字単位で完全に同一の出力**（該当の1文が毎回同じ箇所で欠落）だった。念のため4回目も実行し、同じ結果を確認した。
- `whisper-server`（`/inference` に `language=ja` で3回POST）も、**3回とも文字単位で完全に同一の出力**（該当の1文を含む全文）だった。
- **結論：どちらも実行のたびに結果がぶれるような非決定的な現象ではない。** 同じ入力・同じパラメータなら常に同じ結果になる（＝ランダム性の問題ではなく、パラメータ設定の問題）。
