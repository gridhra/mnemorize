# 要件ドラフトv0.2：やったことの記録と間隔反復による再提示

- 作成日：2026-09-15（v0.1）、更新：2026-09-15（v0.2）
- 状態：§5の判断10件はすべて推奨案で確定した（2026-09-15、ユーザー承認）。あわせて「利用者は日本語メイン」という横断要件を §3.7に追加した。次は技術検証（§6）と実装計画。
- この文書の読み方：§1は「何を作るか」の解釈、§2は調査で分かったこと、§3は要件案、§4は成功基準、§5はユーザーに判断を求める論点、§6は次の一手。調査の詳細は `docs/research/01〜04` にあり、本文書は結論だけを引く。

## 0. 用語（この文書の中で使う言葉）

- **記録（エントリ）**：「今日やったこと」1件。音声文字起こし・手入力・画像添付で作る。復習の単位でもある。
- **日（デイ）**：記録を束ねる日付。1日に0件以上の記録がある。
- **復習キュー**：その日に期限が来ている記録の一覧。
- **自己評価**：復習時にユーザーが選ぶ「どれだけ思い出せたか」。次回期限の入力になる。
- **間隔反復**：思い出せた記録ほど次の提示を遠くへ延ばす方式の総称。
- **FSRS**（Free Spaced Repetition Scheduler）：現行Ankiの標準アルゴリズム。「安定度・難易度・想起確率」の3変数で次回期限を計算する。
- **自由再生**：手がかりだけを見て内容を自分の言葉で思い出すこと。穴埋めや選択ではない。

## 1. ニーズの読み取り

### 1.1中心にあるニーズ（要件ラフから読み取れること）

1. **想起の単位は「問題」ではなく「その日やった学習・作業のエピソード」**。フラッシュカード型を明示的に排除しているのは、カードをQ/Aに分解する手間が間隔反復を続かなくさせる最大要因であり、それを設計から取り除きたいから、と解釈する。
2. **記録行為そのものを想起訓練にしたい**。「やったことを口で説明する」行為が当日の自由再生になる。したがって音声入力は利便性だけでなく学習効果の一部であり、「録音のしやすさ」は主要件になる。
3. **アプリの責務は「いつ何を思い出すか」の管理に限定する**。正誤判定はしない。自己評価で十分。
4. **日付を軸にした容器**（デイリーノート型）。1日0..n件。カード=記録1件。
5. **画像添付**は「ノートの写真」「ホワイトボード」「コードのスクリーンショット」のような、復習時の答え合わせ材料と解釈する。

### 1.2作らないもの（スコープ外を明文化）

- Q/A形式のカード作成、穴埋め（cloze）、正誤判定、採点。
- クラウド同期、複数ユーザー、モバイルアプリ（将来の配布はmacOS個人配布までを視野に入れる）。
- 学習時間の集計・グラフ（勉強記録アプリの領域。必要なら後で）。

### 1.3先行事例から借りる設計方針（詳細はresearch/01）

- 復習画面は「手がかり → 本文全文表示 → 自己評価」。答えを隠す仕掛けは要らない（Obsidianのノート単位レビュー、ReadwiseのDaily Reviewが前例）。
- 1日の提示件数に上限を設ける。間隔反復アプリの離脱原因で最も繰り返し指摘されるのは「溜まった量」であり、借金を作らない設計が要る。
- 評価は粗い段階（3段階程度）にとどめる。
- 音声・画像の添付を持つ復習リマインダーは日本製reminDOに前例があり、方向性は珍しくない。

## 2. 調査で分かったこと（結論のみ。出典はresearch/02〜04）

### 2.1ローカル音声認識（research/02）
- Homebrewの `whisper.cpp` 1.9.4がmacOS 26 / arm64向けに用意済み。Metal対応、Core ML有効化でNeural Engineも使える。CLIとHTTPサーバーの両方がある。
- 日本語精度は2026年のベンチマークでWhisper large-v3-turboとQwen3-ASR-1.7Bが上位。ただし20クリップの小規模ベンチマークで、専門用語混じりの独り言での再現性は未確認。
- whisper.cppは16kHzモノラル16bit WAVしか受け付けない。ブラウザ側でWeb Audio APIを使って直接その形式を作ればffmpegは不要。
- 日本語特有の課題：句読点が付きにくい、無音でのハルシネーション、専門用語の誤変換。対策は無音トリミング、短い用語リストのプロンプト、句読点の後処理。

### 2.2アプリ形態とデータ（research/03）
- 初期実装が最速で、後から配布形態（Tauri 2）に移しやすいのは「Bun + HonoのローカルWebアプリ+ SQLite +ブラウザUI」。Whisperはサブプロセス呼び出し。
- SQLiteを正本、Markdown/JSONは常時書き出せる派生物。画像はファイル実体で保持しDBにはパスとハッシュ。SQLiteをiCloud Driveに直接置くのは危険なので、日次スナップショットを同期フォルダに置く。
- 復習履歴は追記専用にし、スケジュール状態はそこから再計算できる導出値として持つ。アルゴリズムを後から差し替えられる。
- 記録の加筆修正履歴は全文スナップショットで残す（文字起こし誤りの修正を戻せるように）。

### 2.3スケジューリング（research/04）
- 推奨はFSRS-6（ts-fsrs 5.4.2、2026-09-10更新）を既定パラメータで使い、評価をAgain / Good / Easyの3段階にする。FSRSは「前回からの実経過日数」を入力に取るので、サボった日の遅延を自前ロジックなしで吸収できる。
- 代替は固定ラダー（1-3-7-14-30-60-120-365日）。挙動が説明可能で依存ゼロ。レビューログの形式を共通にしておけば後からFSRSへ移れる。
- 自由再生向けの評価基準は「本文を開く前に要点を何個言えたか」で切ると一貫しやすい（これは設計提案で、検証研究はない）。
- 編集しても復習履歴は自動ではリセットしない。明示操作でのみリセット。当日中の再提示（learning steps）は入れない。間隔365日超で自動卒業＋手動卒業。
- 注意：FSRSの既定パラメータは一問一答カードの統計から来ており、トピック単位の自由再生への適用は外挿。実データで様子を見る前提で採用する。

### 3.7日本語メインの利用者への配慮（横断要件）

利用者の母語は日本語。記録の大半は日本語で、英語の専門用語が混じる。以下は他の節の要件すべてにかかる。

| # | 要件 | 優先度 |
|---|---|---|
| J1 | UIの文言・日付・ボタン名はすべて日本語。評価ボタンも日本語（例：「思い出せなかった」「思い出せた」「余裕だった」）とし、英語のAgain/Good/Easyは内部名にとどめる。 | 必須 |
| J2 | 音声認識は言語を日本語に固定（自動判定させない。自動判定は短い発話で英語・中国語に誤判定しやすい）。英語の専門用語はそのまま英字で出ることを許容する。 | 必須 |

## 4. 成功基準の素案

- 記録1件が、録音開始から保存まで60秒以内に終わる（文字起こし待ちは並行で進む）。
- 毎日の復習が10件・10分以内に収まる。
- 3日サボったあとの翌日に、上限10件の中で回復できる（キューが心理的負債にならない）。
- 1か月継続時点で「作るのが面倒」「評価に迷う」が主観的に起きていない。

## 5. ユーザーに判断を求める論点

各論点に「前提 → 選択肢 → 推奨」を書く。**2026-09-15にユーザーがすべて推奨案で承認し、確定した。**確定内容の一覧：D1=B（ローカルWebアプリ）、D2=A（FSRS-6）、D3=A（3段階）、D4=B（タイトル任意＋先頭1文）、D5=B（復習メモはv1以降）、D6=A（上限10件）、D7=A（明示リセットのみ）、D8=A（音声保存）、D9=A（復習対象外トグル）、D10=A（午前4時境界）。以下は判断時の比較の記録として残す。

### D1.アプリ形態
- 前提：個人利用を最短で始めたい。将来配布は望ましい。
- A：Tauri 2で最初から作る。配布形態が最初から整うが、Rustビルド・モデル同梱・マイク権限で「動くまで」が長い。
- B：Bun + HonoのローカルWebアプリ+ SQLite +ブラウザUI。最速で動く。Whisper呼び出し層を薄く分離しておけば、後でTauriに殻を替えられる。
- C：Python（FastAPI）+ SQLite。faster-whisperをプロセス内で使えるが、Apple Siliconではwhisper.cppより遅く、配布でPython同梱が重い。
- **推奨：B**。理由は「動くまでが最短」「ts-fsrsと同じ言語」「移行経路が確保されている」。

### D2.スケジューリング方式
- A：FSRS-6（ts-fsrs）既定パラメータ。遅延吸収が自動。ブラックボックス感あり。
- B：固定ラダー1-3-7-14-30-60-120-365日。説明可能。遅延の扱いを自前で決める必要。
- **推奨：A**。導入コストはAもBもほぼ同じで、Aは「サボった日」の扱いを設計しなくて済む。レビューログの形式を共通にしてBへ戻れるようにする。

### D3.自己評価の段階数
- A：3段階（Again / Good / Easy）。
- B：4段階（Again / Hard / Good / Easy）。FSRS本来の形。
- **推奨：A**。自由再生ではHardとGoodの境界が主観に流れ、Anki自身もHardの誤用が間隔を壊すと警告している。

### D4.復習時の「手がかり」に何を見せるか
- 前提：音声文字起こしにはタイトルがない。手がかりが本文全部だと想起訓練にならない。
- A：タイトル必須入力。手間が増える。
- B：タイトル任意。未入力なら本文の先頭1文を自動で手がかりにする。復習画面はタイトル（または先頭1文）＋作成日＋添付枚数を見せ、「開く」で全文。
- C：手がかりは作成日とタグだけ。最も想起負荷が高い。
- **推奨：B**。記録の手間を増やさず、後からタイトルを付け直せる。

### D5.復習時の口頭想起の録音（復習メモ）
- 前提：「話すこと自体が想起訓練」という考えを復習にも延長できる。
- A：v1から入れる。復習画面に録音ボタン、文字起こしを復習履歴に添付。
- B：v1では入れず、記録側の録音が安定してから追加する。
- **推奨：B**。v1の完成を早めるため。データモデルには復習メモ欄を最初から用意しておく（後付けが楽）。

### D6.溜まったときの扱い
- A：1日の上限10件、期限超過が長い順。超過分は翌日以降に自然に回る。
- B：上限なし。期限超過を全部出す。
- **推奨：A**。上限値は設定可能にする。

### D7.記録の編集と復習履歴の関係
- A：編集は履歴に影響しない。「最初からやり直す」チェックを明示的に入れたときだけリセット。
- B：本文の変更量が大きければ自動でリセット。
- **推奨：A**。誤爆で履歴を失わない。

### D8.音声ファイルの保存
- A：保存する（WAV、3分で約6MB）。再文字起こしと復習時の聞き直しに使える。
- B：文字起こし後に破棄する。ディスクを節約。
- **推奨：A**。容量は年1〜2GB程度の見込みで、後から一括削除の機能を付ければよい。

### D9. 「復習対象にしない」記録を許すか
