## 結論（先に）

**既存のデータを壊したり失わせたりする経路は見つからなかった。**追記専用の復習履歴
（`review_logs`）と現在の予定（`schedule_state`）は1つのトランザクションで一緒に書かれており、
添付の削除もファイル1つと行1つの対応が保たれている。`/files/` のパス脱出は防がれている。
文字起こしの禁止事項（`-nt` を付けない、`-l ja` を付ける）はどちらも守られており、実機で
実際に音声を流して、`-nt` を付けたときに落ちていた文が今回は出力に含まれることを確認した。

**一方で、「誤動作」に分類される問題を8件見つけた。**そのうち最も重いのは次の2つである。

1. **自動卒業が起きた直後に取り消しを行うと、卒業状態が戻らない**（下記D-1）。
   復習の予定だけが1手戻り、記録は卒業したまま残る。以後その記録は復習に二度と出てこない。
   実際に再現させて確認した。
2. **書き出し（Markdown）が、画像ファイルが1つ欠けているだけで途中で500エラーになり、
   全体が完了しない**（下記D-3）。バックアップの経路が静かに使えなくなる。実際に再現させた。

また、**取り消し（undo）と「予定を最初からやり直す」（要件S4）は、サーバー側のAPIは
できているのに画面のどこからも呼べない**（下記F-1、F-2）。文言も
`web/src/i18n/ja.ts` に `undo:'取り消す'` として用意されたまま使われていない。
つまりD-1の問題は、現状では画面から踏むことができない（APIを直接叩いた場合のみ起きる）。
逆に言えば、取り消しボタンを画面に足す前にD-1を直す必要がある。

現状の自動テストは99件すべて通り、型検査（`bun run typecheck`）も無警告だった。

## 各項目の詳細

### D-1（誤動作）自動卒業の直後に取り消すと、卒業が戻らない

**場所**：`server/services/reviews.ts:300`（`undoLastReview`）。関連して同ファイル233〜290行（`submitReview`）。

**何が起きるか**。評価を記録する `submitReview` は、間隔が365日に達したときに2つのことを同時に行う。
(a) `entries.retired_at` に時刻を入れて卒業させ、(b) `review_logs` に `kind='retire'` の行を1つ積む。
ところが取り消しの `undoLastReview` は、`kind='review'` の行を1つ消して予定を作り直すだけで、
(a)も(b)も元に戻さない。結果、予定は1手前に戻るのに記録は卒業したままになり、
復習キューは卒業済みを除外するので、その記録は二度と出てこなくなる。
画面には「取り消しました」と出るため、ユーザーには気づけない。

**再現手順と結果**（実際に実行した）。新しい記録を作り、「余裕だった」（rating 4）を繰り返して
間隔を伸ばした。5回目で間隔が367日になり自動卒業が働いた（`auto_retired: true`、
`retired_at: 2028-03-09T12:00:00.000+09:00`）。続けて `undoLastReview` を呼んだところ、
`retired_at` は `2028-03-09T12:00:00.000+09:00` のまま変わらず、`review_logs` には
`kind='retire'` の行が残ったままだった。

**直し方の案**。`undoLastReview` のトランザクションの中で、消す評価行より後に積まれた
`kind='retire'` の行も一緒に消し、その行が存在したときだけ `entries.retired_at = NULL` に戻す。

**補足**：現状この経路は画面からは踏めない（F-1のとおり取り消しボタンが無いため）。
取り消しボタンを画面に出す作業と、この修正は同時に行うのが安全である。

**関連して確認した点**：自動卒業の判定そのものは正しかった。`log.scheduled_days >= 365` で
「以上」を見ているので、ts-fsrsが評価順を保つために間隔を366・367日へ押し上げる場合
（調査ノート `docs/research/05-spike-fsrs.md` が「365日以内を不変条件にするな」と書いている件）でも
取りこぼさない。設定 `auto_retire` をfalseにすると卒業しないことも、既存テストが確認している。

### D-2（誤動作）「今日」画面の日付だけがシステム時計を直接読む

**場所**：`server/routes/days.ts:20`。
`const resolved = date === 'today' ? localDate(new Date(), boundaryHour()) : date`

**何が起きるか**。プロジェクトの規約（`CLAUDE.md`）は「時刻は `server/adapters/clock.ts` の
`now()` を通す」と定めている。`now()` は環境変数 `MNEMORIZE_FAKE_NOW` があればその時刻を返す仕組みで、
「翌日になったら復習に出る」といった日付をまたぐ動作を一晩待たずに確かめるためのもの。
この1か所だけ `new Date()` を直接呼んでいるため、`MNEMORIZE_FAKE_NOW` が効かない。

**再現手順と結果**（実際に実行した）。`MNEMORIZE_FAKE_NOW=2026-09-20T10:00:00` でサーバーを起動し、
2つのAPIを叩いた。`/api/health` は `"today":"2026-09-20"` を返したのに、
`/api/days/today` は `{"date":"2026-09-15", ...}` と実際の日付を返した。
画面を開くと「今日」タブだけが本物の今日を指し、他の画面と食い違う。

**直し方の案**。`import { now as clockNow } from '../adapters/clock.ts'` を足し、
`localDate(new Date(), …)` を `localDate(clockNow(), …)` にする。

**同じ規約違反が他に11か所ある**（下の「時刻の扱い」節に一覧）。ただし他の箇所は
引数の既定値として `new Date()` を書いているもので、日付の表示や検証には影響しない。
唯一この `days.ts` だけが、検証用の時刻上書きを実際に壊している。

### D-3（誤動作）画像が1つ欠けるとMarkdown書き出し全体が止まる

**場所**：`server/services/exporter.ts:69`。
`await copyFile(join(dataDir(), a.rel_path), join(attachDir, …))`

**何が起きるか**。書き出しは日付ごとにループして、各記録の画像を `export/attachments/` にコピーする。
`copyFile` は、コピー元のファイルが無いと例外を投げる。この例外を誰も受け止めていないので、
書き出し全体が500エラーで終わる。その時点までに書いた日付のファイルは `export/` に残るので、
中途半端な書き出しが「完了したもの」と見分けがつかない状態で残る。
添付を消したあとにファイルだけ手で消した、外部同期の途中でファイルが無い、といった場面で起きる。

**再現手順と結果**（実際に実行した）。記録を1件作り、PNGを1枚添付し、データディレクトリから
そのPNGの実体を削除してから `GET /api/export/markdown` を叩いた。返ってきたのは
`{"error":"サーバー内部でエラーが起きました"}`（HTTP 500）で、それ以前に書かれた
`export/2026/2026-09-20.md` はディスクに残ったままだった。

**直し方の案**。`copyFile` をtry/catchで包み、失敗した画像はMarkdownのリンクを出さずに
飛ばして、書き出し結果に「欠けた画像」の一覧として返す（`ExportResult` に1フィールド足す）。

### D-4（誤動作・未確認）文字起こしの反映とジョブ完了が別々にcommitされる

**場所**：`server/services/transcribe.ts:306`（`runJob` の中の `applyToEntry(job, post.text)` の呼び出し）と、
その直後307〜325行の `UPDATE transcription_jobs … SET status = 'done'`。

**事実**。`applyToEntry` は記録の本文に文字起こし結果を追記する（既存の記録があれば末尾に、
無ければ新しい記録を作る）。この書き込みは `updateEntry` の中で1つのトランザクションとして確定する。
そのあと別の文として、ジョブの行に `status='done'` を書く。2つは同じトランザクションに入っていない。
そして両方を囲む `try { … } catch { finishFailed(…) }` があるので、
後半だけが失敗すると、本文は書かれたのにジョブは `failed` になる。

**推論**（未確認）。ジョブが `failed` になると画面に「再試行」ボタンが出る。押すと
`retryJob` が同じ音声をもう一度処理し、`applyToEntry` がもう一度同じ文章を本文末尾に追記する。
つまり同じ段落が二重に入る。サーバーが落ちて `status='running'` のまま残った場合も、
起動時の後始末（`recoverStaleJobs`）がそのジョブを `failed` に倒すので、同じ経路に入る。
この二重追記は実際には再現させていない（後半の書き込みだけを失敗させる必要があり、
今回の環境では起こせなかった）。機構としては成立していると考える。

**直し方の案**。`applyToEntry` の呼び出しとジョブ行の `UPDATE` を1つの `db.transaction(() => { … })()`
にまとめる。あるいは、ジョブ行に「本文へ反映済み」の印を持たせ、`retryJob` がそれを見て
二度目の追記をしないようにする。

### D-5（誤動作）設定の値を検証せずに保存する

**場所**：`server/services/settings.ts:49`（`putSettings`）。
既知のキーかどうかだけを見て、値は `JSON.stringify` してそのまま保存している。

**何が起きるか**。読み出し側（`boundaryHour()`、`limitOf()`、`hallucination_phrases` の
`Array.isArray` 判定）はそれぞれ壊れた値を既定値に読み替えるので、サーバーは落ちない。
問題は `auto_retire` で、読み出し側が `getSettings().auto_retire === true` という
厳密な比較をしているため、**文字列 `"yes"` が入ると自動卒業が黙って無効になる**。
設定画面には「有効」と見えるのに効かない、という状態になりうる。

**再現手順と結果**（実際に実行した）。
`PUT /api/settings` に `{"daily_review_limit":"abc","hallucination_phrases":"not-an-array","auto_retire":"yes","boundary_hour":99}`
を送ったところ、そのままの値が保存され、`GET /api/settings` がその値を返した。
サーバーは落ちず、`/api/health` の `boundary_hour` は4に丸められて表示された。

**現状の画面からは起きない**。`web/src/pages/Settings.tsx:64-75` が保存前に数値と配列に直しており、
`auto_retire` は画面に項目自体が無い（つまり既定値trueのまま触れない）。
したがって今の重大度は「誤動作の芽」であって、実害はまだ出ない。

**直し方の案**。`putSettings` の中で、キーごとに型を検査して合わないものは捨てる
（`DEFAULT_SETTINGS` の値の `typeof` と比べるだけでも大半は防げる）。

### D-6（不便）同じ秒に3回目のスナップショットを作ると失敗する

**場所**：`server/services/snapshot.ts:23-29`。

**何が起きるか**。ファイル名は `mnemorize-YYYYMMDD-HHmm.sqlite`。既にあれば秒を足した
`mnemorize-YYYYMMDD-HHmmSS.sqlite` を試す。フォールバックはこの1段だけなので、同じ秒に3回目を作ると
また衝突し、`VACUUM INTO`（既存ファイルには書けない）が例外を投げて500になる。

**再現手順と結果**（実際に実行した）。`POST /api/export/snapshot` を続けて3回叩いた。
1回目 `mnemorize-20260915-1225.sqlite`、2回目 `mnemorize-20260915-122508.sqlite`、
3回目が `{"error":"サーバー内部でエラーが起きました"}`。

**直し方の案**。連番を末尾に足すループにする（`-2`、`-3`… と、空いている名前が見つかるまで）。

**あわせて確認した点**：古いスナップショットの削除ロジックは正しかった。
ファイル名を辞書順に並べると作成時刻順になり（`1225.sqlite` の `.` は `122508.sqlite` の `0` より
文字コードが小さいので、秒付きの名前が後に来る）、`slice(0, 全体 - 14)` で古い側だけを消す。
最新が消される組み合わせは見つからなかった。

### D-7（不便）WAVでないデータを送ると500になる

**場所**：`server/adapters/audio-files.ts:28`（`parseWavHeader` が投げる `WavParseError`）。

**何が起きるか**。`WavParseError` は `server/services/entries.ts` の `ValidationError` を継承していないので、
`server/app.ts:33` のエラー処理がこれを「入力の誤り（400）」と判別できず、
「サーバー内部でエラーが起きました」（500）になる。原因が利用者に伝わらない。

**再現手順と結果**（実際に実行した）。`POST /api/transcriptions` に `not-a-wav` という9バイトを送ると
HTTP 500で `{"error":"サーバー内部でエラーが起きました"}`。

**直し方の案**。`server/routes/transcriptions.ts` の `createJob` 呼び出しをtry/catchで包み、
`WavParseError` を `ValidationError`（「WAV形式の音声を送ってください」）に詰め替える。

### D-8（不便）壊れたURLエンコードで500になる

### F-1（不便）取り消し（undo）が画面から呼べない

**事実**。サーバー側には `POST /api/reviews/:entry_id/undo` があり、
`web/src/api.ts:207` に `undoReview` という呼び出しも用意されている。
文言も `web/src/i18n/ja.ts:107-108` に `undo: '取り消す'` / `undone: '直前の評価を取り消しました'`
として置かれている。しかし `web/src` 全体を検索しても `undoReview` を呼んでいる箇所は無く、
復習カード（`web/src/components/ReviewCard.tsx`）にも取り消しボタンが無い。
つまり「押し間違えの救済」という機能が、部品だけ揃って画面に出ていない。

**直し方の案**。`ReviewCard` の評価直後、または `web/src/pages/Review.tsx` の
「記録しました」の通知の横に取り消しボタンを出す。ただしD-1（自動卒業が戻らない）を
先に直すこと。直さずに出すと、自動卒業した記録を取り消したユーザーが記録を失う。

### F-2（不便）「予定を最初からやり直す」が画面から呼べない

**事実**。要件S4の「内容を作り直したので最初から」はサーバー側に実装されており
（`server/services/reviews.ts:356` の `resetSchedule`、`PATCH /api/entries/:id` の
`reset_schedule` フラグ）、テストも通っている。`web/src/api.ts:196` の型定義にも
`reset_schedule?: boolean` がある。しかし編集画面（`web/src/components/EntryEditor.tsx`）に
このフラグを立てる操作が無く、`web/src` 内でこのフラグを渡している箇所は1つも無い。

### F-3（不便）whisperの標準エラー出力がそのまま画面に出る

### T-1（整理）マイグレーションの連番に0002が欠けている

**場所**：`server/db/migrations/` に `0001_init.sql` と `0003_transcription.sql` があり、`0002_*.sql` が無い。

**何が起きるか**。実行器（`server/db/migrate.ts`）はファイル名を辞書順に並べ、
まだ適用していないものを順に流す。今の状態では問題は起きない。

0003が作った列を0002が前提にする、といった順序の逆転が起きうる。

**直し方の案**。`0002` は永久に欠番と決めて、その旨を `server/db/migrations/` に
1行のメモ（または空の `0002_skipped.sql`）として残す。新しい変更は0004から始める。

### T-2（整理）データベースのコピーがHTTPで取得できる

**場所**：`server/routes/files.ts` はデータディレクトリ全体を配信する。

**評価**。ネットワークを使わない個人用ローカルアプリなので、実害は小さい。ただし

**直し方の案**。`/files/` が受け付けるパスを `attachments/` と `audio/` の2つの接頭辞に限る

### T-3（整理・未確認）購読解除の関数が別の購読集合を消す場合がある

**場所**：`server/services/transcribe.ts:62-66`（`subscribe` が返す購読解除の関数）。

```
return () => {
  set.delete(fn)
  if (set.size === 0) listeners.delete(jobId)
}
```

**推論**（未確認）。返す関数は、作られた時点の `set`（購読者の集合）を閉じ込めている。
いったんその集合が空になって `listeners` から外れ、あとから同じジョブIDに別の購読者が現れて
**新しい集合**が作られたあと、古い解除関数をもう一度呼ぶと、`set.size === 0` が成立して
`listeners.delete(jobId)` が走り、新しい集合ごと消えてしまう。
その購読者には以後イベントが届かない。実際に起こすには解除関数を2回呼ぶ必要があり、
今の呼び出し側（進捗配信の `finally`）は1回しか呼ばないので、現状では起きないと考える。

**直し方の案**。解除時に `listeners.get(jobId) === set` を確かめてから消す。

### T-4（整理・未確認）進捗配信で15秒のタイマーを解除していない

**場所**：`server/routes/transcriptions.ts:94-100`。

```
await new Promise<void>((resolve) => {
  notify = resolve
  setTimeout(resolve, 15000)
})
```

**事実**。イベントが届いて `notify()` が呼ばれても、`setTimeout` は解除されない。
タイマーは15秒後に必ず発火する（そのとき `resolve` は既に解決済みなので無害）。
セグメントが速く届くとタイマーが積み上がる。上限は15秒ぶんなので深刻ではない。

**推論**（未確認）。より気になるのは、利用者が画面を閉じたときにこのループが終わるかどうか。
ループを抜ける条件は「ジョブが終わる」か「`writeSSE` が例外を投げる」のどちらかで、
接続が切れたことを直接見ていない（Honoの `stream.onAbort` を使っていない）。
Honoの実装で切断後の `writeSSE` が例外を投げるのかどうかは今回確認できなかった。
投げない場合、ジョブが終わるまで15秒ごとのpingを書き続け、購読も解除されない。

**直し方の案**。`setTimeout` の戻り値を `clearTimeout` し、`stream.onAbort(() => { finished = true; notify?.() })`
を足してループを抜けられるようにする。

### T-5（整理）リセット前の評価を取り消すと、履歴だけが消える

**場所**：`server/services/reviews.ts:306`（`undoLastReview` が消す行の選び方）と
`server/services/reviews.ts:333`（`rebuildState` が使う行の絞り込み）。

**何が起きるか**。取り消しは `kind='review'` の最新行を消す。一方、状態の作り直しは
`entries.schedule_reset_at` より後の行だけを使う。
「予定を最初からやり直す」を実行した直後（リセット後の評価がまだ0件のとき）に取り消すと、
**リセット前の古い評価が1件、状態に何の影響も与えないまま履歴から消える**。
`review_logs` は「追記専用」と設計されているので、この削除は設計意図に反する。

**直し方の案**。`undoLastReview` の行の選択に `AND reviewed_at > COALESCE(:reset_at, '')` を足し、
リセット後の評価が無ければ「取り消せる評価がありません」を返す。

### T-7（整理）手がかり文の組み立てが2か所にある

### T-8（整理）添付削除の順序

`server/services/attachments.ts:63` は、データベースの行を消してからファイルの実体を消す。
途中で落ちると実体だけが残る（記録は消えないので、データの損失ではなくゴミが残るだけ）。
逆順（ファイル → 行）にすると、落ちたときに行だけが残って画像が壊れて見えるので、
**今の順序のほうが安全**である。指摘としては「そういう設計である」と記録しておく意味の項目で、
直す必要は無いと考える。

### スケジューラ（ts-fsrsの使い方）

守るべき規約は調査ノート `docs/research/05-spike-fsrs.md` に書かれている。1つずつ照合した。

### 文字起こしの経路

禁止事項は調査ノート `docs/research/06-spike-whisper.md` に書かれている。

- **`-nt`（`--no-timestamps`）が付いていない**。`server/adapters/asr-whisper-cli.ts:186-199` の
  引数の組み立てを読み、`-nt` が無いことを確認した。さらに**実機で確かめた**。
  調査ノートで「`-nt` を付けると丸ごと落ちた」とされている音声
  （`spikes/whisper/samples/sample_a.wav`）をアプリのAPI経由で処理したところ、
  落ちていたはずの「あと、Reactの…クリーンアップ関数の実行タイミングを実装しながら確認した。」と
  「依存配列に指定した値が変わるたびに…」の2文が、どちらも出力に含まれていた。
  ジョブは `status: done`、セグメント5件。**この問題は再現しない。**
- **`-l ja` がある**。同じ箇所で確認。上記の実機テストでも日本語として正しく認識された。
- **標準出力のパーサと `-oj` のJSONが矛盾しない**。両者は同じ `AsrSegment`
  （`from_ms` / `to_ms` / `text`、ミリ秒）を作る。標準出力側（`parseSegmentLine`）は
  `[00:00:00.000 --> 00:00:05.120] 本文` の形を読み、JSON側（`segmentsFromJson`）は
  `offsets`（ミリ秒の数値）を優先して、無ければ `timestamps`（文字列）を同じ関数で変換する。
  最終結果はJSONを優先し、JSONが読めないときだけ標準出力の結果を使う設計になっていて、
  ミリ秒という単位が両方で揃っている。上記の実機テストで、保存されたセグメントの
  `from_ms`/`to_ms` が妥当な値（0 → 27220 → 34460 → 46960）であることを確認した。
- **ハルシネーション句の照合が前後の空白・句読点を落として行われる**。
  `server/services/transcribe.ts:81`（`normalizeForMatch`）が空白・句読点・記号を除き、
  小文字化してから**完全一致**で判定する。部分一致では消さない（本当に話した文の中に
  その言い回しが出てきた場合に消さないため）。既存テスト4件がこれを確認している。
  なお `normalizeForMatch` は文字列の**途中**の句読点も落とすので、規約の文面
  （「前後の空白と句読点を除いた完全一致」）より少しだけ広く一致する。
  実害は考えにくいが、意図どおりかは実装担当に確認する価値がある。
- **全セグメントが定型句だった場合**は `post.empty` が立ち、ジョブを
  「音声を認識できませんでした」で `failed` にする（`server/services/transcribe.ts:295`）。
  記録は作られない。既存テストあり。
- **同時実行1のキューが例外で詰まらない**。`runJob` の中で文字起こし本体が
  try/catchに包まれているので、失敗しても次のジョブに進む。実際に、モデルが処理できない
  0.1秒の無音WAVで2件のジョブを連続で投入したところ、**2件とも `failed` で決着し、
  キューは詰まらなかった**。
- **タイムアウト時に子プロセスをkillしている**。`server/adapters/asr-whisper-cli.ts:205-208` で
  `setTimeout` から `proc.kill()` を呼び、そのあと `await proc.exited` で終了を待ってから
  失敗にしている（既定10分）。
- **一時ファイルの後始末**。`-oj` が書くJSONは、成功・失敗・タイムアウトのどの経路でも
  `unlink(jsonPath).catch(() => {})` で消される。上記の実機テスト後に

- **サーバー再起動時の取り残し**。`recoverStaleJobs()` が `status='running'` のまま残った行を
  `failed` に倒す。最初にジョブへ触れたときに1度だけ走る。既存テストあり。

### データを壊す・失う経路

- **`/files/*` のパス脱出**：防がれている（D-8の節に再現の詳細）。
- **添付削除のファイルと行の不整合**：1行と1ファイルが1対1で、行を消してからファイルを消す。
  ファイルだけが残るゴミの可能性はあるが、記録が見えなくなる方向の壊れ方はしない（T-8）。

- **書き出しの上書き**：Markdown書き出しは同じ日のファイルを毎回上書きするが、
  中身はデータベースから作り直したものなので、これは意図した動作である。
  JSON書き出しは `mnemorize-export-YYYYMMDD-HHmm.json` と時刻入りの名前で、上書きしない。
- **SQLの文字列連結**：`server/` 全体のSQLを読んだ。すべてプレースホルダ（`?`）で、
  ユーザー入力をSQLに連結している箇所は無い。全文検索も

  `GET /api/days/1%27%20OR%201=1`（引用符を含む日付）を投げたところ、
  日付形式の検証でHTTP 400になった。
- **ファイル名にユーザー入力が混ざらないか**：混ざらない。添付も音声も
  `Bun.randomUUIDv7()` で名前を付け、拡張子はMIMEから引いた固定の表
  （`server/services/attachments.ts:8-16`）から選ぶ。アップロード時の元のファイル名は使わない。
- **添付のMIMEと拡張子の対応**：上記の表でpng / jpeg / gif / webp / heicに限られ、
  表に無いMIMEは400で拒否される。1枚20MBの上限もある。
  同じ記録に同じ内容（SHA-256が一致）の画像を足しても、既存の行を返して二重保存しない。
